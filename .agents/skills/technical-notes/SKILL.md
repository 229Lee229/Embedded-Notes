# 技术笔记整理

把技术交流整理成可独立阅读、持续积累的一份 Markdown 文档。默认侧重原理及实现机制，省略不影响理解的具体配置参数，内容尽可能简洁，提炼重要信息。

## 确定笔记位置

- 用户指定文件时使用该文件；否则在当前项目根目录查找既有技术笔记，默认使用 `技术笔记.md`。
- 同时存在多份候选且无法判断时，先询问目标文件。不要把笔记写进技能安装目录。
- 先阅读目标文档的结构与相关节点。技术点使用二级标题，例如 `## printf 节点`；同义标题应归入同一节点。
- 同一技术点合并、补充或纠正既有节点；新技术点追加节点。保留用户自己的文字和其他节点，避免重复整段问答。

## 整理内容

从用户指定的交流范围提取已讨论的结论及原因。结合相关源码、已取得的构建证据或官方资料核对关键事实；只读取理解该节点需要的材料。

按技术点选用以下内容，保持已有文档风格，不必为不适用的项目创建空标题：

1. **问题与核心原理**：说明该机制解决什么问题、为什么这样实现。
2. **调用或数据过程**：从入口到结果写清先后关系；必要时用简短流程图或时序示例。
3. **关键实现**：选取最小但足以解释机制的代码，说明每段代码的作用。区分实际源码摘录、原理示意和建议实现。
4. **底层机制**：有硬件关系时说明寄存器、状态位、缓冲区、中断或 DMA 的作用；软件问题则说明内存、类型或接口约定等相关机制。
5. **设计取舍与边界**：解释替代方法为什么不同、函数返回意味着什么，以及会改变结论的重要前提。
6. **验证与来源**：给出适量源码位置、已有验证证据或官方文档链接，并标明尚未验证的部分。

写成连贯的技术说明，使另一位读者无需查看聊天记录即可理解。默认使用中文，保留原始函数和寄存器名称。

## 内容取舍与准确性

- 以原理和实现为主。波特率、引脚、晶振、内存地址等具体配置值通常省略；若某个值是理解机制的必要条件，解释其作用或使用符号参数。用户明确要求记录配置时再保留实际值。
- 关键代码保留必要的类型、条件和顺序，不能为了省略参数而删掉有意义的逻辑。
- 区分通用原理和特定芯片、编译器或 C 库的实现。例如 `printf` 是否调用 `fputc` 应依据实际 C 库和链接证据，不能一概而论。
- 区分“交流中建议”“源码已实现”“编译已通过”“硬件已验证”。不能把建议代码写成已经生效的工程行为。
- 注释、宏名和旧笔记不能替代实际实现。例如存在缓冲区大小或超时宏，并不代表发送队列或超时机制已经实现。
- 只保留与当前技术点有关的必要补充，避免复制整本手册或引入无关知识。
- 文件和资料链接尽量使用相对于笔记文件的路径；外部资料使用实际官方链接。不要写死用户名、盘符或依赖某台电脑的工具安装路径。

## 保存与检查

- 保存为 UTF-8 Markdown，检查标题层级、代码围栏、表格与链接。
- 使用 Mermaid 时，将含中文或标点的节点文本放在双引号中，优先使用兼容的基础语法。若有解析器或预览工具，检查实际解析结果；不能仅凭代码围栏配对就认为图表语法正确。
- 若用户反馈图表解析报错或预览空白，优先将相关图表改成等价的 `text` 代码块或文字步骤，保留技术内容；实际预览未确认时不要声称预览已恢复。
- 确认一个技术点只有一个主节点，原有无关内容保留，重复内容已合并。
- 检查示例的类型、调用先后及重要状态位语义；只整理文档时不要顺带修改固件源码或启动编译、烧录。
- 完成后简短说明本次更新的节点、提供笔记文件链接，并报告影响使用的未确认项。

本技能只在用户要求整理、保存或更新技术笔记，或明确调用时执行文件写入；普通技术问答本身不自动改写笔记。
